# 0. 摘要（先看这一页）

## 0.1 PoC 到底证明了什么

PoC 证明的是一件**结构性**的事，而不是一堆数字：

> 把"说完 → 判停 → 选工具 → 决策"这条串行链，改成"用户还在说就已经在算"，**核心链路能跑通、每段恰好 1 次有效决策、投机被推翻能正确取消、一段说完能连续消费下一段**。整句判停二分类 94.6%【实测】，中文最后一字→LLM 启动 755ms【实测】。

PoC **没有**证明的是：判停判得准（中文前缀误判说完率 62.1%【实测】）、决策选得对（未做大样本验证）、真实车控敢不敢接（全程 mock）、百万车扛不扛得住（单进程单会话）。

## 0.2 五个最关键的判断

| # | 判断 | 性质 | 一句话依据 |
|---|---|---|---|
| **J1** | **判停质量是唯一无法靠工程绕过的硬门槛**，而且纯文本方案在该架构下已到物理上限 | 【实测】+【判断】 | 中文按句 97.4% 的句子至少有一个前缀被误判"说完"【实测】；每句真正可用的判停结果只有 1.2 条，不是覆盖率问题而是"落地即过期"【实测】。编排层已经压过一轮（849→501ms），再抠毫秒没有意义 |
| **J2** | **判停必须从"云侧文本打分"改成"端侧音频模型"**，这条同时解决质量、延迟、KEV 单点、QPS 成本四个问题 | 【判断】 | 文本判停看不到韵律；端侧模型（Smart Turn 类，8MB int8，社区实测 CPU 10–65ms）把一趟网络 RTT 直接删掉，且不再需要每句 8.83 次远程调用【实测调用量】 |
| **J3** | **"决策正确率"是当前最大的未知数**，它比延迟更危险：延迟差是体验问题，决策错是责任问题 | 【实测】缺口 | 全部验收里唯一被测过的"94.6%"是**判停二分类**，不是决策正确率（`README.md` 里那句"决策正确率（held-out）94.6%"是口径错误，见附录 B）。242 工具里 192 个 `non_idempotent`【实测】 |
| **J4** | **安全边界不能由模型判，必须由确定性产品规则判**，而现有规则只覆盖了 8/242 个工具 | 【实测】+【判断】 | 确认池 8 个工具，池外 234 个永不确认【实测】；二次确认真实判中 81% < 85% 门槛且有 2 处护栏泄漏（"行吧"0.946、"就那个吧"0.867 会被执行高危动作）【实测】 |
| **J5** | **成本与容量是"量产才暴露"的第二类硬门槛**，单实例 KEV 架构在百万车量级差 1–2 个数量级 | 【假设】量级估算 | 每轮 14.73 次 KEV 调用【实测】× 100 万车 × 20 轮/天 ≈ 2.95 亿次/天，日均 3.4k QPS、峰值约 27k QPS【假设：车数/轮数】，而当前 KEV 是**单台远程实例 + 两条 SSH 隧道**（隧道只做流隔离，不是扩容）【实测】 |

## 0.3 最该先拍的三件事

1. **判停技术路线**：继续投纯文本 prompt 调优，还是直接切端侧音频模型 + 文本兜底（推荐后者，见 ADR-2）。
2. **安全责任边界**：语音助手能不能碰"安全相关执行器"（ADAS/ESP/制动/充电），还是只允许碰"舒适类执行器"、安全类一律转人工或拒绝（推荐后者，见 ADR-5）。
3. **自研/第三方边界**：ASR、判停、LLM、TTS 四项分别自研还是采买（决定了团队编制与商务谈判窗口，见 ADR-3）。

## 1.2 必须同时读进去的三条"反直觉"结论

1. **覆盖率 ≠ 可用率**。把判停覆盖率从 3.3% 拉到 95.0%，可用判停结果几乎没变（1.20 → 1.21 条/句）【实测】。原因是判停往返（~265ms）必然长于前缀间隔（150ms）——**"每个前缀都有分"和"每个前缀的分都能用"是两件事**。这直接说明：在现有架构上继续加并发/加前缀只会烧钱，不会变快。
2. **并发不是万能的，而且已经实测把一个方向否掉了**。判停并发有效（覆盖 42.1%→70.0%→93.9%，同时更快）【实测】；但**选工具并发有害**——工具调用 5.55→10.75 次/句，p50 从 849ms 恶化到 1503ms，还挤占了同一台 KEV 的判停调用（13.35→7.45 次/句）【实测】。这条经验在量产架构决策里会反复用到：**同一后端上的并发，收益取决于它是否在做"去饥饿"，而不是"并行"**。
3. **延迟长尾不在编排层**。p90 在三组配置下恒为 1504ms【实测】——长尾由"判停结果到达晚 / 确认窗 / 网关方差（1-token 请求都能跑 1.0–2.9s）"决定。所以量产不能靠继续优化编排，只能靠**换判停输入模态**（音频）和**换决策调用方式**（流式）。

# 2. 量产差距分析

## 2.0 总览：10 个维度，先分清"真门槛"和"工程量"

**真门槛（★ = 必须在架构层解决，加人加时间也绕不过去）**：判停质量、端云架构、安全边界、成本容量 —— 这四条错了，整个方案要重做。
**工程量**：ASR 声学、真实工具、延迟预算、合规认证、并发鉴权、可观测 —— 量大、有不确定性，但路径是清楚的。

| # | 维度 | 差距等级 | 是否硬门槛 | 是否可在 P0–P1 内闭环 |
|---|---|---|---|---|
| 1 | 判停质量与音频/韵律判停 | 🔴 极高 | **★ 是**（体验的地基） | 部分（P0 验证 + P2 量产化） |
| 2 | ASR 量产化（噪声/回声/双人/方言/断网） | 🔴 高 | **是** | 否（依赖 P2 车规测试） |
| 3 | 端侧 vs 云侧架构 | 🔴 高 | **★ 是**（成本/可用性/隐私同源） | 部分（P1 定型） |
| 4 | 真实工具执行与车辆能力打通 | 🔴 高 | **是**（demo 与产品的分界线） | 部分（P0 打通 1–2 域） |
| 5 | 延迟与体验目标 | 🟡 中 | 否（但需重新定预算） | 是（P1） |
| 6 | 安全与功能安全 | 🔴 极高 | **★ 是**（不可谈判） | 部分（P1 规则、P2 认证） |
| 7 | 车规与合规 | 🟡 中 | 是（但节奏由认证驱动，不阻塞开发） | 否（P2） |
| 8 | 并发/多用户/账号/鉴权/灰度 | 🟠 中高 | 否（工程量问题，不阻塞 P0） | 是（P1） |
| 9 | 成本 | 🟠 中高 | **★ 是**（百万车量级会否决架构） | 是（P1 建模、P2 优化） |
| 10 | 可观测性与线上质量闭环 | 🟠 中高 | 否，但**决定能否迭代** | 是（P1，务必早做） |

下面逐维展开。每条给：**差距 / 为什么是硬门槛 / 不解决的后果**。

## 2.1 判停质量与音频/韵律判停

**差距**
- 中文前缀误判说完率 62.1%、按句 97.4%【实测】——即几乎每一句中文都至少有一个前缀被误判成"说完了"。
- 判停输入是**纯文本**（`score_eot(text)` 只吃 `utterance` 字符串，见 `src/turn_eot.py`）【实测】，看不到语调、拖音、语速、气息。
- 三问 prompt 是**原样照抄英文配置** `r2_en_utter_only`【实测】——中文场景从一开始就是"借用英文判停 prompt"。
- 中文最后一段的延迟达标（755ms）靠的是 `confirm_silence_ms=700` + 投机，而不是判停判得准【实测】。

**为什么是硬门槛**

判停是整条流水线的**唯一状态来源**（`PROJECT-POC.md` §1.3：状态机只依赖判停支路）。判停错一次，直接导致两种用户可见后果：
- **误判说完** → 提前开口/提前执行，用户还在说 → 抢话，或者更糟：**执行了一个用户还没说完的指令**；
- **漏判说完** → 用户等 2s 兜底 `max_silence_ms` 才被确认 → "它要愣一下才理我"，正是本项目要消灭的体感。

而且这是**纯文本方案的物理上限**：模型拿到的是 ASR 已经丢掉了韵律的文本，中文里"我想去"和"我想去。"在文本上几乎不可分（实测 `我想去` margin 仅 +0.0111）【实测】。继续调 prompt 的收益边界很窄。

**不解决的后果**
- 体验上：量产必须把 `confirm_silence_ms` 拉到 700ms 以上来防误触发【实测默认值】，这本身就吃掉了 700ms 的延迟预算——也就是说**判停不准，所有延迟优化都会被确认窗抵掉**；
- 正确性上：误判说完会触发决策；242 工具里 192 个是 `non_idempotent`【实测】，一次误执行就是一次投诉/事故；
- 成本上：为防误判而开投机，浪费率在 600ms 韵律下达 75.9%【实测】——**用真金白银买"不抢话"**。

**方向（判断）**：接音频/韵律判停模型（Smart Turn 类），端侧推理；文本判停降级为"兜底/二次校验"，而不是主判据。

## 2.2 ASR 量产化

**差距**
- PoC 的 ASR 是**火山豆包 v3 sauc 云端流式**，麦克风链路只在"安静办公室 + 合成语音/近场说话"下验过【实测】。
- 感知链路最大的一块就在这：**音频静音 → ASR 文本定稿 270–1330ms**【实测】。这一块 PoC 明确划到范围外。
- 没有：车内噪声（胎噪/风噪/空调/音乐）、AEC 回声（TTS 正在播时用户插话）、双人同时说话、方言/口音、断网降级。【实测：全部未做】
- 没有独立的端侧 VAD：麦克风模式用 ASR 断句的 `utterances[].end_time` 代理"VAD 结束"，且**只用于展示、不进状态机**【实测】。

**为什么是硬门槛**

车内是语音识别最恶劣的消费级声学环境之一，而**ASR 端点（endpointing）直接决定判停的输入时刻**。当前"音频结束 → 文本定稿"就吃掉 0.27–1.33s，如果量产目标里端到端预算是 1s 级（§2.5），这一项单独就能把预算吃光。另外 TTS 一上线，**没有 AEC 就没有 barge-in**——而 barge-in 是本项目"准全双工"卖点的必要条件。

**不解决的后果**
- 车内在 80km/h 工况下识别率断崖，用户回到"按按钮说话"；
- TTS 播放时用户无法打断，产品退化成对讲机；
- 断网即失能（当前无一行业务可用）。

## 2.3 端侧 vs 云侧架构

**差距**

当前所有能力都在云侧（判断项均已标注）：

| 环节 | 现在在哪 | 实测延迟 | 网络依赖 |
|---|---|---|---|
| VAD | 无独立 VAD（浏览器 `ScriptProcessorNode` 采集，20ms 分帧）【实测】 | — | 有 |
| ASR | 云侧（火山豆包） | 握手 170ms、partial ~500ms、final +110ms【实测】 | **强** |
| 判停 | 云侧 KEV（远程 `106.53.0.235:8009`，两条 SSH 隧道）【实测】 | p50 121ms 单发 / 会话内 340–556ms【实测】 | **强**，且是单点 |
| 选工具 | 云侧 KEV（同实例） | 每句 5.90 次调用【实测】 | **强** |
| 决策 | 云侧 LiteLLM 网关 + `deepseek-v4.1-flash` | 1.4–2.9s 非流式【实测】 | **强** |
| TTS | 不存在 | — | — |

**为什么是硬门槛**

三个理由叠加成一条：**判停必须在端侧**。
1. **延迟**：判停放云侧，每句多一趟 RTT（实测会话内 340–556ms）【实测】；放端侧，音频在本地，判停可与 ASR 并行、无需等网络。
2. **单点**：KEV 是单台远程实例，两条隧道只是"流隔离"，不是冗余【实测】。云端判停挂了，整个车机变哑巴——这在量产是不可接受的失效模式。
3. **容量/成本**：每轮 14.73 次远程 KEV 调用【实测】，百万车量级是日均 3.4k QPS、峰值 ~27k QPS【假设：100 万车 × 20 轮/天】，单实例绝无可能。

**不解决的后果**
- 网络抖动直接变成"助手卡住"（当前断网即完全不可用）；
- 地库/隧道/高速弱信号区（恰恰是车内高频场景）体验崩塌；
- 成本随车数线性上升且无上限（每次交互都在调云）。

## 2.4 真实工具执行与车辆能力打通

**差距**
- 242 个工具的 `binding` **全部是 `mock`**【实测】（`fixtures/tools-core-score.yaml` 242/242）。
- 无 CAN/以太网信号适配层、无服务发现、无权限模型、无超时/重试/幂等/回滚语义【实测：全部未做】。
- 参数校验在量产必需，而 PoC 里对细粒度工具集的严格参数引用校验**已降级为 warn**（`argument_validation_warning`）【实测】。
- 工具集来自一份导出的 schema 快照（`core_tool_schemas_score.json`，242 tools / 17 domains）【实测】，**没有 Owner、没有版本化、没有变更流程**。

**为什么是硬门槛**

mock 执行意味着"决策对了"和"车真的动了"之间没有任何被验证过的环节。量产要回答的全是这里的问题：这个工具是哪个 ECU 提供的？调不通怎么办？执行到一半断网怎么办？同一个请求重发两次会不会开两次引擎盖？某车型没有这个执行器怎么办？——**这些没有一个在 PoC 里被碰过**。

**不解决的后果**
- 决策层再准也落不了地；
- 重复执行（`non_idempotent` 工具 192 个【实测】）会直接造成物理后果；
- 工具集一旦要改，没有版本化就会"改一处坏一片"。

## 2.5 延迟与体验目标

**差距**

PoC 只定义了"最后一字 → LLM 启动 ≤800ms"这一个门槛，而且英文 1501ms 已 FAIL 并被接受【实测】。量产需要的是**端到端**预算，当前实测拼出来的链路是：

```
音频结束  ──270~1330ms──►  ASR 文本定稿  ──~700ms(确认窗)──►  判停确认
          ──14ms(调度)──►  LLM 请求发出  ──1400~2900ms──►  决策返回  ──?──►  TTS 首音
```
（数字全部【实测】：270–1330ms 来自 `spec-latency-opt.md` §1；确认窗 700ms 是默认 `confirm_silence_ms`；14ms 是"都就绪→请求发出"；1400–2900ms 是非流式决策往返。TTS 一段不存在）

**建议的量产端到端预算（【判断】+【假设】，需产品确认）**

| 环节 | 建议目标 | 依据 |
|---|---|---|
| 音频结束 → VAD/端点判定 | ≤ 200ms | 端侧 VAD 常规水平【判断】 |
| → 判停结论（含确认窗） | ≤ 300ms | 端侧音频模型 10–65ms【外部资料】+ 短确认窗【判断】 |
| → LLM 首 token | ≤ 400ms | 必须流式；当前非流式 1.4–2.9s 不可接受【实测】 |
| → TTS 首音 | ≤ 200ms | 流式 TTS 常规水平【判断】 |
| **合计（音频结束 → 首音）** | **≤ 1100ms（P50），≤ 1800ms（P90）** | 【假设】需与产品/竞品对标后定稿 |
| 打断（barge-in）响应 | ≤ 300ms | 需要 AEC【判断】 |

**为什么是门槛（但不是最硬的那条）**

延迟差是体验问题、可迭代；但如果预算不定，工程会把力气花在错的地方——PoC 已经证明"编排层再优化收益有限"（p90 恒 1504ms）【实测】。

**不解决的后果**：三条链路各自优化、合起来仍超标；TTS 上线后总延迟再涨一截，才发现预算从来没算过。

## 2.6 安全与功能安全

**差距**
- 危险动作的判定是**确定性的池**（8 个工具）+ KEV 三问裁决，池外 234 个工具永不确认【实测】。
- 真实判中率 81% < 85% 门槛，且**两处护栏泄漏**：`行吧`（0.946）、`就那个吧`（0.867）会被判 agree 并**真的执行**高危动作（关 ADAS、开引擎盖）【实测】。
- 无回滚、无撤销、无审计日志（PoC 明确不做动作回滚）【实测】。
- 无"这个工具属于哪个安全等级"的元数据（`side_effect` 只有 idempotent/non_idempotent 两值）【实测】。
- 二次确认的 `AGREE_FLOOR=0.75` / `CLEAR_MARGIN=0.15` / takeover ≥0.5 是**经验阈值**，未按工具风险分级【实测】。

**为什么是硬门槛**

这是唯一"错了不可修复"的维度：动作不可撤销（开引擎盖要手动关、解锁充电枪物理断开），责任在人不在模型。而且**行业惯例是把 AI 排除在安全路径之外**（【判断】，见 ADR-5）：语音可以请求，但执行安全相关动作必须走车辆既有的安全机制与人工确认，不能由概率打分决定。

**不解决的后果**
- 一次误执行 = 一次事故/召回级事件；
- 无法通过功能安全评审（SOTIF 视角下"AI 误判"就是预期功能不足）；
- 责任无法界定 → 保险与法务无法背书 → 项目无法上市。

## 2.7 车规与合规

**差距**
- 无数据分类与留存策略（语音/音频是否出境、留多久、谁能取）【实测：未做】。
- 无账号/身份/授权绑定（谁在开车、谁能下这个指令）【实测：未做】。
- 未评估：功能安全（ISO 26262 边界）、预期功能安全（SOTIF/ISO 21448）、网络安全（ISO 21434 + UN R155/R156）、个保法与汽车数据规定、EU AI Act 的透明度义务【待核实：具体条款适用性】。
- 云侧依赖：ASR 走火山（外部云）、LLM 走公司内网 LiteLLM、KEV 走单台远程机【实测】——**数据流向跨了三方**，量产要先画清数据流图。

**为什么是硬门槛（但节奏不同）**

认证不是"写代码时能顺便搞定"的事，它有自己的周期（【判断】6–18 个月量级，视范围），所以**必须与开发并行启动、且在架构定型前介入**——架构定完了才发现数据出境不合规，代价是重做。

**不解决的后果**：车型无法准入（欧洲尤其）、语音数据被认定违规采集、AI 交互未披露。

## 2.8 并发 / 多用户 / 账号 / 鉴权 / 灰度

**差距**
- PoC 是**单进程单会话**：`ui/server.py` 里 `MIC_SESSIONS` 只保留最近 8 轮，一个 server 进程同时只跑一个 mic 会话【实测】。
- 无鉴权（WS 直连，无 token）、无会话隔离、无重连恢复、无多用户、无灰度、无配置下发【实测：全部未做】。
- `TurnConfig` 是进程内硬编码默认值（18 字段）【实测】，不是按车型/场景下发的配置。
- 消费游标不持久化，断线即丢【实测】。

**为什么不是最硬的那条**

这一维是**已知工程量的工程问题**，没有科学不确定性；但它是"量产的必要条件"，且会反向约束架构（服务化 = 会话状态要外置，而当前状态机是**单写者线程 + 内存态**设计【实测】）。

**不解决的后果**：无法做 OTA 灰度、无法按车型差异化、无法定位线上问题、并发稍微一高就串话。

## 2.9 成本

**差距（量级估算，全部【假设】，需用真实报价替换）**

| 项 | 每轮次数【实测】 | 100 万车 × 20 轮/天【假设】 | 说明 |
|---|---|---|---|
| KEV 判停调用 | 8.83 | 1.77 亿次/天 | 只为"每个前缀都有分"，其中 97% 落地即过期【实测】 |
| KEV 选工具调用 | 5.90 | 1.18 亿次/天 | |
| **KEV 合计** | **14.73** | **2.95 亿次/天（日均 3.4k QPS，峰值 ~27k QPS）** | 当前为单实例【实测】 |
| LLM 决策调用 | 1.0（投机下 1.03–1.76） | 2000 万–3500 万次/天 | 浪费率 3.4%【实测，150ms 韵律】～75.9%【实测，600ms 韵律】 |
| LLM 预热 | 1 次 1-token | 2000 万次/天 | 计费未知【假设：按可忽略】 |
| ASR 音频 | 1 路流 | — | 按并发/时长计费 |

**为什么是硬门槛**

PoC 的架构是"用调用次数换延迟"：判停 8.83 次/句、选工具 5.90 次/句，都是**为了提前量而多花的钱**。这个换算在小规模是划算的，在百万车量级需要有明确的成本模型与上限（【判断】每交互成本需压到"分"级，而不是"角"级）。

**不解决的后果**：商务模型算不过来 → 项目在量产评审阶段被财务否决（这类否决通常发生在架构已定型之后，代价最大）。

## 2.10 可观测性与线上质量闭环

**差距**
- PoC 的证据体系很强：`timeline.json`（每事件带 `t_ms` + `text_version`）、SSE 与落盘同格式、`summary()` 20+ 字段、前缀评测产出 detail.jsonl/csv【实测】——**这是可以直接继承的最大资产**。
- 但它只覆盖"单机会话"，缺：线上集中采集、按车型/版本聚合、错误分桶、坏例回流、自动评测（eval）集与金标管理、版本对比（A/B）【实测：全部未做】。
- 判停/决策的**金标集不存在**：`natural_complete` 是 LLM 自标且偏宽松【实测】；决策正确率无金标。

**为什么是门槛（但不是技术门槛）**

没有线上数据闭环，判停模型和 prompt 的迭代就是"盲调"。PoC 里 `natural_complete` 自标导致的统计口径问题【实测】已经预示了这件事：**没有金标，所有指标都可疑**。

**不解决的后果**：上线即"不可迭代"——出了问题只能靠用户投诉定位，模型无法迭代，成本无法优化。

# 3. 关键架构决策清单（ADR）

格式：决策点 / 可选项 / 推荐 / 判断依据 / 不决策的代价。**每条都建议在 P1 结束前落纸**。

## ADR-1 端云分工：ASR / TTS / 判停 / LLM 分别放哪

| 环节 | 可选项 | 推荐 | 依据 |
|---|---|---|---|
| VAD + 音频判停 | 云侧 / 端侧 | **端侧（必须）** | 省一趟 RTT（会话内实测 340–556ms）【实测】；消掉 KEV 单点【实测】；消掉 8.83 次/句远程调用【实测】；模型可做到 8MB int8【外部资料】 |
| ASR | 纯云 / 纯端 / 端云级联 | **级联**：端侧小模型保底（车控等高频短指令）+ 云侧大模型主用 | 断网可用是量产底线【判断】；云端精度更高【判断】 |
| 判停的文本兜底 | 保留 / 去掉 | **保留但降级**：仅在音频模型不确定区（如 0.4–0.6）做二次校验 | 已投入的三问与 margin 机制可直接复用（`turn_eot.py` 45 行）【实测】 |
| LLM 决策 | 纯云 / 端侧小模型 / 级联 | **级联**：高频确定性指令（导航回家、开空调）端侧规则+小模型；长尾/多步走云侧大模型，且必须流式 | 决策 1.4–2.9s 非流式不可接受【实测】；成本按调用次数计【假设】 |
| TTS | 云侧 / 端侧 | **端侧流式 TTS**（首音延迟敏感）或云侧流式 + 端侧预缓冲 | 首音 ≤200ms 目标下云侧 RTT 太贵【判断】 |

**不决策的代价**：端云边界会在 P1 被"逐条 case 打补丁"的方式随机决定，最后既没有离线降级也没有成本上限，且 P2 认证时才发现数据流不合规。

## ADR-2 判停技术路线：纯文本 / 音频模型 / 混合

| 选项 | 优势 | 劣势 |
|---|---|---|
| A. 继续纯文本（调 prompt / 换中文专用模型） | 零端侧成本、改动最小、现有代码直接可用 | 看不到韵律；实测已到边界：按句中文 97.4% 有前缀误判【实测】；跨语言迁移差（英文 23.8% vs 中文 62.1% 说明 prompt 与语言强耦合）【实测】 |
| B. 端侧音频/韵律模型（Smart Turn 类） | 直接用 PCM，看得到语调/拖音/语速；本地推理无 RTT；开源可自托管（BSD-2-Clause、8MB int8、23 语种含中文）【外部资料】 | 需端侧算力与实测；中文车内侧需自建评测集；模型只是"说完/没说完"二分类，`wait`（让我想想）语义要另做 |
| C. 混合（音频主判 + 文本兜底 + 语音活动量特征） | 兼顾：音频判"韵律上说完没"，文本判"语义上是否完整"，两路不一致时降级到"再等一等" | 工程复杂度最高；需要两套评测集与融合规则；错误归因变难 |

**推荐：C 的收敛形态 —— 音频模型为主判据（端侧），文本判停仅作"语义完整性"二次校验，且只在 margin 落在模糊区时才调用。**

判断依据（三条，都可追溯到实测）：
1. 纯文本的天花板已被实测钉住（1.2 条/句可用）【实测】；
2. 编排层优化已到边界（p90 恒 1504ms）【实测】；
3. 端侧音频模型的外部可行性已成立（8MB int8、10–65ms、多语种）【外部资料，待本机实测】。

必须承认的**代价（【判断】）**：`wait` 态（"等一下我想想"）纯音频模型给不出来，必须保留文本/意图层判断；这正是推荐 C 而非 B 的原因。

**不决策的代价**：P0 会把两周时间花在"再调一版中文 prompt"上，然后拿回一个可能只从 62.1% 降到 50% 的数字，且无法解释为什么。

## ADR-3 模型选型与供应商策略（自研 vs 第三方、单点风险）

**现状【实测】**：ASR = 火山豆包（外采）；判停 = KEV 远程单实例（内部服务，单点）；决策 = 公司 LiteLLM 网关 + `deepseek-v4.1-flash`（内部网关，单模型，代码里还硬校验了 endpoint 与模型名，`existing_slow_configuration()` 会直接抛错）；TTS = 无。

| 决策点 | 推荐 | 依据 |
|---|---|---|
| ASR | **双供应商**（主 + 备），抽象成统一流式接口 | 当前单供且强网络依赖【实测】；车厂量产普遍要求二供【判断】 |
| 判停 | **自研/自托管开源模型**（端侧），保留文本兜底 | 端侧部署 + 可微调 + 无调用成本；BSD 许可可商用【外部资料，待法务确认】 |
| 决策 LLM | **不绑单一模型**：抽象成 provider 接口，至少 2 家可切换，按场景路由（端侧小模型 / 云侧大模型） | 当前代码硬校验单一 endpoint+模型名【实测】，这在量产是可用性风险；模型价格与能力月级变化【假设】 |
| TTS | 采买为主 | 不在本项目能力圈【判断】 |

**明确的风险提示**：现在"决策必须来自 deepseek-v4.1-flash @ 指定网关"是**写死在代码里的**（`core_pipeline_run.py` L207-209）【实测】。量产必须把"选哪个模型"从代码变成配置，否则换模型=改代码=重新认证。

**不决策的代价**：单供应商涨价/降级/停服时无 Plan B；模型版本一变，历史评测全部失效且无法解释。

## ADR-4 工具/技能协议：242 工具如何量产化、谁维护、如何版本化

**现状【实测】**：242 工具 / 17 域；`binding: mock` ×242；`side_effect` 只有 idempotent(50) / non_idempotent(192) 两值；来自一份 schema 快照；两阶段打分（17 域 → 域内工具，batch 40，top-3）靠 **prompt 拼工具描述**打分，没有向量检索。

| 决策点 | 推荐 | 依据 |
|---|---|---|
| 工具描述与协议 | **保留 KEV 两阶段打分**（已验证 5.90 次/句、p50 数百 ms【实测】），但增加**结构化字段**：`owner`、`version`、`risk_level`、`supports_offline`、`precondition`、`confirmed_by` | 现在打分只依赖自然语言 description，等于把"这个工具能不能碰"交给了模型【判断】 |
| 谁维护 | **工具注册中心（registry）+ 域 Owner**，语音团队只做 schema 校验与准入 | 242 个工具横跨 17 个域，语音团队不可能懂每个执行器【判断】 |
| 版本化 | 工具 schema 独立版本号 + 变更需过"召回回归集"（top-3 命中率、参数合法率） | 两阶段打分对描述文本敏感，改一句话就可能改召回【判断】 |
| 规模增长 | 242 → 更多时，**域内必须加检索**（embedding 或关键词），不能继续靠 batch 40 全打分 | 单次请求压到 ≤40 工具是为时延做的妥协【实测】；工具翻倍即失效【判断】 |
| 参数校验 | **从 warn 恢复成硬校验**，且按工具 schema 生成 | 现在是 `argument_validation_warning`，只告警不拦【实测】；量产必须拦住非法参数 |

**不决策的代价**：242 个工具会变成"没人敢改、没人知道谁能改"的黑盒；一次 schema 变更静默破坏召回，线上表现为"助手突然听不懂了"。

## ADR-5 安全边界：哪些动作必须二次确认、能否撤销、如何审计

| 决策点 | 推荐 | 依据 |
|---|---|---|
| 安全相关执行器（ADAS/ESP/制动/充电/引擎盖） | **不由语音助手直接执行**：只允许"发起请求 → 车辆既有安全机制/人工确认" | AI 不进安全路径是行业惯例【判断】；现有池内 8 工具全部是这类动作【实测】 |
| 二次确认的裁决 | **确定性规则优先**：高危动作要求"两次独立确认"或"明确肯定句模板"，模型只做"是否明确同意"的二值判断，**不做语义推断** | `行吧`(0.946)、`就那个吧`(0.867) 已实测穿透 `AGREE_FLOOR=0.75` 并会执行【实测】——说明"概率阈值 + 语义模型"这条路在含糊口语上不可靠 |
| 可撤销性 | 定义三级：**可撤销**（媒体/空调/座椅）/ **可补偿**（导航改道）/ **不可撤销**（开引擎盖、解锁充电枪、关 ADAS）。不可撤销类必须双确认 + 提示不可逆 | 现在无回滚能力【实测】；但"不可撤销"的分类可以纯规则做 |
| 审计 | 每次决策 + 每次执行 + 每次确认裁决**全量留痕**（谁、何时、什么意图、哪个工具、什么参数、判停/确认分数、是否执行） | 现有 timeline 事件体系已具备雏形【实测】，扩展即可 |
| 风险等级来源 | 由 `risk_level` 字段（ADR-4）驱动，不由模型判断 | 现在"问不问"是产品规则的 8 项白名单【实测】，这是**正确**的设计，要扩大到全量工具并加分级 |

**不决策的代价**：安全边界会以"每出一个 bug 补一条规则"的方式长出来，最终既不可解释也不可认证；一旦发生误执行，无法证明系统当时"尽力了"。

## ADR-6 会话架构：单进程 → 服务化

**可选项**：A. 继续单进程（PoC 形态）；B. 有状态服务（会话粘性 + 内存态）；C. 无状态服务 + 外置会话状态（Redis/流存储）。

**推荐：C**。依据：当前状态机是"单写者线程 + 内存态 + 版本校验"【实测】，`tick()` 是唯一状态迁移入口（`PROJECT-POC.md` §2.3.1）——这个设计对单个会话是干净的，但无法横向扩展；把会话状态外置（或按会话 ID 路由 + 定期快照）是唯一能同时支持重连、灰度、多租户的路径。

**不决策的代价**：P1 的服务化会退化成"给 Flask 加 gunicorn"，然后在第一次真实并发时串话。

## ADR-7 配置与策略下发

**现状【实测】**：`TurnConfig` 18 字段是进程内默认值（`eot_margin=0.2`、`confirm_silence_ms=700`、`max_silence_ms=2000`、`eot_max_inflight=3`、`tools_max_inflight=1`、`speculative_llm=True`…），UI 里可改但只在单次会话内生效。

**推荐**：配置分层 —— **车型级（硬件/网络能力）→ 场景级（驻车/行驶/后排）→ 会话级（用户偏好）**，全部可下发、可回滚、可按车机版本灰度。特别地：`speculative_llm` 开/关是**产品策略而不是调参**（开=755ms 但浪费率可到 75.9%；关=0% 但 1159ms）【实测】，必须由产品而非工程决定。

**不决策的代价**：不同车型用同一套参数，低端车机被投机策略拖垮，高端车机被保守参数浪费。

# 4. 目标架构（量产版）

## 4.1 架构图

```
车端（SoC · 实时域）                              ← 所有"必须在 100ms 内出结论"的事都在这里
├─ 音频前端：麦克风阵列 → AEC / 降噪 / 波束成形    ← TTS 播放中可打断的前提
├─ 端侧 VAD（Silero 类）──► 端侧音频判停（Smart Turn 类）
│                          8MB int8 · 10–65ms · 本地推理 · 无网络依赖
│                          输出：complete / cut / wait（+ 置信度）
├─ 回合状态机 ◄─────────────────────────────────── 继承 PoC TurnSession
│    五态 · 消费游标 · 投机决策 · 取消/作废 · 版本校验 · 单写者
├─ 端侧 ASR 兜底（离线短指令：车控 / 空调 / 媒体基础）
├─ 端侧小模型 / 确定性规则决策（高频指令直接出结果，不绕云）
├─ 端侧流式 TTS（首音 ≤200ms）
└─ 车辆能力网关（本地）：权限校验 · 幂等 · 审计 · 回滚 · 超时
        │                                        │
        │ QUIC / WS（断线可续、可降级）            │ CAN / 车载以太网
        ▼                                        ▼
云侧（区域化部署）                            车辆执行器（ECU）
├─ 流式 ASR 主用（双供应商，主 + 备）
├─ 决策 LLM 池（流式 · 多模型 · 按场景路由）
├─ 工具语义检索（242 工具 / 17 域 → top-3 短名单）
├─ TTS 长文本合成
├─ 会话服务：鉴权 · 状态外置 · 灰度 · 配置下发 · 限流降级
└─ 质量闭环：全量埋点 · 坏例回流 · 金标集 · 离线评测 · 模型版本对比
```

**读图要点**：判停、VAD、状态机、车控执行四条链路**全部在端侧闭环**，云侧只承担"需要大模型能力"的部分（高精度 ASR、长尾决策、长文本 TTS）。这是与 PoC 最大的结构差异——PoC 里判停和决策都在云侧【实测】。

## 4.2 组件职责与"能不能复用"

| 组件 | 职责 | 与 PoC 的关系 | 结论 |
|---|---|---|---|
| 端侧 VAD + AEC | 语音活动检测、回声消除（TTS 期间可打断） | PoC 无独立 VAD（用 ASR `end_time` 代理，且只做展示）【实测】 | **新做** |
| 端侧音频判停 | 判定"韵律上说完没" | PoC 是云侧文本 KEV 三问（`turn_eot.py`，45 行） | **新做**，但三态语义（complete/cut/wait）与 margin 机制**直接继承** |
| 回合状态机 | 五态 + 消费游标 + 投机 + 取消 + 版本校验 | `turn_session.py`（854 行）是项目最核心资产【实测】 | **直接复用逻辑，需重构成无状态可外置** |
| 端侧 ASR 兜底 | 离线短指令识别 | 无 | **新做** |
| 流式 ASR 主用 | 在线高精度识别 | `asr_stream.py`（250 行，火山 v3 sauc 帧协议）【实测】 | **适配层复用**，需抽象成多供应商接口 |
| 工具语义检索 | 242 工具 → 短名单 | 两阶段 KEV 打分（17 域 → 工具，top-3）【实测】 | **复用 + 加检索 + 加结构化字段** |
| 决策 LLM 池 | tool_call / ask_user / done | `decide()`（选择型 prompt，只披露 top-3）【实测】 | **复用 prompt 形态**，必须改流式 + 多模型 |
| 二次确认闸门 | 高危动作判"问不问 / 同意吗" | `confirm_gate.py` + `confirm_orchestrator.py`【实测】 | **规则层复用**，裁决层需重做（见 ADR-5） |
| 车辆能力网关 | 执行、权限、幂等、审计、回滚 | 完全不存在（`binding: mock` ×242）【实测】 | **必须重写（从零）** |
| 会话服务 | 鉴权、状态、并发、灰度、配置 | 单进程单会话（`MIC_SESSIONS` 保留 8 轮）【实测】 | **必须重写（从零）** |
| 质量闭环 | 埋点、金标、评测、对比 | `timeline.json` + 前缀评测脚本【实测】 | **复用数据格式，补云端聚合与金标管理** |
| 诊断 UI | 判停卡片流时间线、瀑布条 | `ui/index.html`【实测】 | **降级为内部诊断工具**（很好用，但不当产品界面） |

## 4.3 一句话总结架构演进

> **PoC 的价值在"状态机 + 消费游标 + 投机记账 + 证据体系"这四件东西；量产要去掉的是"云侧判停"和"mock 执行"，要新建的是"端侧音频链"和"服务化"。**

| 项 | 内容 |
|---|---|
| **目标** | 规模化交付与持续运营 |

| **R2** | **端侧音频判停中文车内侧精度不足**（社区模型是通用域，车内噪声 + 中文口语特性不同） | 中 / 高 | P0 先做可行性验证再投入；准备"文本兜底 + 音频主判"的混合降级；预留自建中文车内数据微调 | 前缀误判率下降不足 30%（对比 62.1%）；不同车速下指标漂移大 |

| **R4** | **成本/容量在量产阶段否决架构**（14.73 次/轮远程打分 × 百万车） | 中高 / 高 | P1 建成本模型并设上限；判停端侧化（把 8.83 次/句打到 0）；工具打分加检索减少 batch | 单车轮次超预期（>20/天）；峰值 QPS 逼近单实例上限；商务报价高于预期 2 倍 |
| **R5** | **单点依赖导致大规模不可用**（KEV 单实例、单一 LLM 网关且模型名硬编码、单一 ASR 供应商） | 中高 / 高 | 判停端侧化（自愈）；LLM 多 provider 抽象（去掉硬校验）；ASR 二供 | 一次隧道/网关抖动即造成会话失败；换模型需要改代码 |
| **R6** | **合规/数据出境结论要求改架构** | 中 / 极高 | P1 就把合规团队拉进来画数据流图；云端区域化部署；音频不留存或端侧脱敏 | 法务首次评审提出"音频不得出境"；TTS/ASR 供应商数据中心位置不明 |
| **R7** | **服务化改造引入并发正确性回归**（现有正确性完全依赖"单写者 + 版本校验"） | 中高 / 中高 | 把 PoC 的确定性验收（C1–C4、A3–A5 的离线 stub harness）**原样搬进 CI**，作为服务化改造的回归网 | 同一 timeline 在两次运行中事件顺序不同；出现 PoC 里从未见过的 `llm_wasted` 计数 |

# 8. 需要 PM / 管理层先拍板的决策清单（按优先级）

| 优先级 | 拍什么 | 不拍的后果 |
|---|---|---|
| **P0-1** | **安全责任边界**：语音助手是否允许直接执行安全相关执行器（ADAS/ESP/制动/充电）；若允许，由谁承担误执行责任 | 架构与确认策略无法定型；P2 认证无法启动；一旦误执行就是召回级事件 |
| **P0-2** | **判停技术路线**：投纯文本调优（便宜、收益有限）还是端侧音频模型（贵、但解决四个问题） | P0 两周可能白花；服务化与端云分工无法定型；成本模型无法估 |
| **P0-3** | **决策正确率的验收门槛是多少**（当前这个数字**不存在**） | 无法判断"能不能量产"；所有质量讨论都悬空；上线后无法回应"它到底准不准" |
| **P0-4** | **投机策略开还是关**（开：中 755ms / 英 1501ms 但浪费率可到 75.9%；关：0% 浪费但中文 1159ms） | 工程无法定默认参数；成本与延迟目标互相打架；这个决策被误当成"调参"（实测里明确写着"这是两个产品策略，不是调参"） |
| **P1-1** | **自研/采买边界**：ASR、判停、LLM、TTS 四项各自的供应商策略与预算 | 团队编制无法定；商务谈判错过窗口；单点风险无法解除 |
| **P1-2** | **端到端时延预算**（音频结束→首音 ≤1100ms 是否成立） | 各链路各自优化、合起来超标；TTS 上线后总延迟再涨一截 |
| **P1-3** | **首发的工具域范围**（242 全上，还是先 3–4 个高频域） | 工具注册中心工作量无法估；QA 范围失控；上线风险不可控 |
| **P2-1** | **合规红线**：音频是否可出境、是否可留存、留存多久 | 架构可能推倒重来（最贵的返工） |
| **P2-2** | **首发车型与市场**（国内 / 欧洲，决定法规集） | 认证范围不清；欧洲市场的 AI Act 披露义务可能改产品文案与交互 |

# 9. 建议的第一步（未来 2–4 周）

原则：**只做能"消掉未知数"的事，不做功能**。五件事按顺序推进，另加一件半天就能做完的安全补丁。

## 第 1 周：把"没有数字"的两个洞补上（可并行）

**① 决策正确率金标集（最高优先，2–3 天启动）**
- 从现有语料（398 句 + `cases/*.jsonl`）挑 200 句，人工标注：`期望工具名 + 关键参数`；另挑 50 句"应该 ask_user"和 50 句"应该 done/拒绝"。
- 用现成 `src/core_pipeline_run.py` 的 `select_tools()` + `decide()` 跑一遍，产出**第一个 top-1 工具正确率数字**。
- 交付：`docs/eval-decision-golden.md` + 一份可重复跑的脚本。**这件事不需要任何新代码，只需要标注 + 跑数**，但它决定项目能不能继续谈量产。

**② 判停"只在停顿上触发"的结构改造（对照实验，2–3 天）**
- 现状：每个前缀都发判停，8.83 次/句，97% 落地即过期【实测】。
- 改法（文档里已明确写为"最值得做的一步"）：文本稳定 ≥X ms 或 VAD `speech_end` 后才发判停。
- 验收口径沿用现有 `streaming_prefix_eval.py`：**判停调用量（目标 ≤2 次/句）+ 可用率（目标 ≥80%）+ 前缀误判率不恶化**。
- 这一步是"纯收益"：降成本（调用量降 4 倍以上）+ 提可用率，且不依赖任何外部采购。

## 第 2–3 周：判停换模态的可行性验证（最大不确定性，先验再投）

**③ 端侧音频判停 POC（这是 P0 的门）**
- 用 Smart Turn v3.2（8MB int8，BSD-2-Clause，23 语种含中文）【外部资料】或等价的音频判停模型，端侧/本机跑推理。
- **关键：必须用同一批中文语料、同一套评测口径**，产出可与 `62.1%` 直接对比的"前缀误判说完率"。语料没有音频就先合成一批（`say -v Tingting` 已验证可用【实测】）+ 录 100 句真人（含车内噪声背景）。
- 交付：一页对照表（纯文本 62.1% vs 音频 X%）+ 单次推理时延 + 端侧资源占用。
- **决策点**：若误判率降不到 30% 以内，说明这条路线也要靠自建数据微调，需要重新评估 P0 周期——**这个结论比代码更值钱**。

**④ 录制车内语料（与③并行，最长链路，今天就约）**
- 200–500 句真人，覆盖：静止/60/80/100km/h、空调最大风量/关、单人说/双人交谈、含 TTS 播放中的插话样本（为后续 AEC 与 barge-in 准备）。
- 这是**所有后续验证（ASR/判停/barge-in）的公共前提**，越晚开始越拖整个 P0。

## 第 4 周：把"demo 与产品之间那条线"往前推一格

**⑤ 真实工具执行打通 1 个只读域（导航或车况）**
- 把 `binding: mock` 换成真实调用（先只读：查询目的地、查车况），带超时、错误码、审计日志。
- 验收：一次真实会话从语音到"真的读到车况"完整跑通；失败路径（超时/权限拒/参数错）有明确用户可见行为。
- 目的不是做功能，而是**把"决策对了 ≠ 车动了"这个鸿沟量化出来**（判断：这条鸿沟会比预期大）。

## 同时可以做的一件小事（半天）

**⑥ 修两处护栏泄漏 + 重跑 L3**：`行吧`(0.946)、`就那个吧`(0.867) 实测会穿透 `AGREE_FLOOR=0.75` 执行高危动作【实测】。加"高危工具双确认"或按工具类别抬门槛，重跑 L3 目标 ≥26/31。半天工作量，消掉一个"召回级"风险敞口。

## 明确不建议现在做的

- ❌ 继续优化编排层毫秒（p90 恒 1504ms，已到边界【实测】）
- ❌ 加判停/工具并发（判停并发已到 3，工具并发实测有害【实测】）
- ❌ 做 TTS 与完整 UI（诊断 UI 已够用，产品 UI 等架构定型）
- ❌ 服务化改造（在判停路线未定之前做服务化，返工概率高）
